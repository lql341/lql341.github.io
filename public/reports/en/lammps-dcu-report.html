Build strategies and issue analysis

2.1 Solution 1: GPU package + HIP backend

Try:Use -D PKG_GPU=ON -D GPU_API=HIP -D HIP_ARCH=gfx936

First result:Compiled successfully, but hung when running

First analysis:GPU package was added by DTK's cmake -xhip compile flag that causes hipcc to generate HIP device code for all .cpp files. HIP initialization stuck while running.

After repair:by setting AMDGPU_TARGETS="gfx936" and disabled HIP_USE_DEVICE_SORT, compiled and run successfully.But performance tests show that the GPU package is 4.6-6.3 times slower than Kokkos(see comparative analysis in Section 6 for details).

2.2 Solution 2: KOKKOS package + HIP backend (architecture mismatch)

Try:Use -D PKG_KOKKOS=ON -D Kokkos_ENABLE_HIP=ON

Result:is compiled successfully, but an error occurs when running:running kernels compiled for gfx906 on gfx936

Analysis:Kokkos 4.6.2 does not support the gfx936 architecture and automatically detects fallback to gfx906. The instruction sets of gfx906 and gfx936 are incompatible, resulting in hipErrorInvalidKernelFile。

2.3 Solution 3: Modify Kokkos source code to support gfx936 (final solution)

Idea:Manually added gfx936 architecture support in Kokkos' cmake configuration and HIP backend code.

📄 Modification 1: lib/kokkos/cmake/kokkos_arch.cmake
Add AMD_GFX936, corresponding mark gfx936; place gfx936 before gfx906 to ensure auto-detection matches gfx936 first; add 936 .
📄 Modification 2: lib/kokkos/cmake/KokkosCore_config.h.in
Add #cmakedefine KOKKOS_ARCH_AMD_GFX936。
📄 Modification 3: lib/kokkos/core/src/HIP/Kokkos_HIP_Instance.hpp
at HIPTraits of WarpSize Added defined(KOKKOS_ARCH_AMD_GFX936). Hygon BW series wavefront size is 64, the same as gfx906/gfx908.
📄 Modification 4: lib/kokkos/core/src/HIP/Kokkos_HIP_IsXnack.hpp
at gpu_arch_can_access_system_allocations to the defined(KOKKOS_ARCH_AMD_GFX936) to return false branch. Hygon DCU does not support system memory access.

2.4 gfx906/Z100: native architecture path

Unlike gfx936, gfx906 (Vega 20) has been natively supported by Kokkos 4.6.2, so there is no need to modify the four architecture files of Kokkos and directly enable Kokkos_ARCH_AMD_GFX906=ON and AMDGPU_TARGETS=gfx906. This reduces architecture porting costs, but DTK 26.04 and the cluster toolchain expose another set of build issues.

2.5 DTK 26.04 cuda_wrappers host mode conflict

When compiled to about 98%,main.cpp because cuda_wrappers/algorithm reported unknown type name '__host__'. LAMMPS Update 5 in cmake/CMakeLists.txt:854 To solve the HIP SFINAE problem of nlohmann/json, put lmp The target is forced to -x c++; hipcc of DTK 26.04 still injects cuda_wrappers in host mode, making the standard <algorithm> was incorrectly parsed.

📄 DTK 26.04 compatible fix
Change the target's -x c++ changed to -xhip --offload-arch=gfx906：
target_compile_options(lmp PRIVATE
  "$<$<COMPILE_LANGUAGE:CXX>:SHELL:-xhip --offload-arch=gfx906>")
The same issue is not reproduced on Platform A in DTK 25.04.2 and is therefore logged as a DTK 26.04 regression rather than a general LAMMPS defect.

2.6 CPU node HSA symbolic chain not available

libhsa-runtime64.so symbolic chain depends on DCU driver directory /opt/hyhal/, the CPU compilation node does not have this directory, so CMake cannot discover the HSA runtime. The solution is to bypass the dead symbolic chain and explicitly change HSA_RUNTIME_LIBRARY points to the real library file in the shared software area; the public command is uniformly written as <DTK_ROOT>/hyhal/lib/libhsa-runtime64.so。

2.7 make damage and login node OOM

Platform B’s system /usr/bin/make ELF interpreter points to non-existent /opt/glibc-2.25/lib/ld-linux.so.2, use the module load compiler/make/4.4. The login node has about 251 GB of memory shared by about 249 users, and the measured available memory is about 46 GB; when hipcc compiles about 1000 C++ files, dcc is terminated by the OOM killer. Finally, the compilation is submitted to the CPU computing queue, applying for 32 cores and about 111 GB of exclusive memory.

2.8 The default three architectures cause three times the compilation pressure

DTK 26.04 default target is gfx906;gfx926;gfx928causes each source file to be compiled three times, amplifying the time and memory overhead. Explicitly execute export AMDGPU_TARGETS=gfx906, only generates target architecture code.

2.9 gfx906 GPU-aware MPI path

All 12 pairs of P2P combinations of the four Z100s on platform B in the same node return hipDeviceCanAccessPeer=1. But DTK 26.04 is missing libhsakmt.a, Unable to build UCX ROCm transport layer. The alternative is to build OpenMPI 5.0.7 from source, using only --with-rocm provides accelerator: rocm and mpiext: rocm, run with shared memory and disable UCX network path:--mca pml ob1 --mca btl vader,self and UCX_TLS=sm,self。

GPU package and Kokkos backend performance comparison

6.1 Test purpose

Verifies whether there is a more efficient GPU acceleration solution than Kokkos. The GPU package uses hand-written optimized HIP kernels that may theoretically be more efficient than Kokkos' general abstraction.

6.2 GPU package compilation repair

Key repair points
  • AMDGPU_TARGETS="gfx936" and GPU_TARGETS="gfx936": Prevent DTK from automatically adding multiple architectures resulting in --offload-arch leaked to g++
  • HIP_USE_DEVICE_SORT=OFF: Avoid linking hip::device, prevent -xhip flag is passed to g++

Analysis of the reasons why the 6.5 GPU package is slow

📌 neighbor list built on CPU: The GPU package output shows "Neigh mode: Hybrid (binning on host)", each reconstruction requires CPU→GPU data transfer, while Kokkos builds the neighbor list entirely on the GPU
📌 GPU package design favors multi-GPU: The single-GPU scenario is expensive and requires additional fix gpu command to manage resources
📌 Kokkos’ GPU execution scope is more complete: pair, neighbor and comm are all executed on the GPU, reducing data transmission between the host and the device

8.3 Changes in GPU acceleration effect after the number of atoms is expanded

📌 GPU acceleration increases as the number of atoms increases: 60× when 32K, estimated ~172× when 1M. Reason: fixed overhead dilution, GPU occupancy increase, calculation/memory access ratio improvement
📌 LJ benchmark GPU utilization is only 20%: Pair calculation accounts for only 6.8%, Modify (CPU side frame) accounts for 76%. LJ is too lightweight and not suitable for GPU optimization
📌 EAM benchmark GPU utilization increased to 41%: Pair calculation accounts for 36.8%, and the calculation amount is 20.7× that of LJ. EAM is a more reasonable GPU benchmark

MPI build and GPU-aware communication configuration

10.1 Background

LAMMPS multi-GPU requires MPI support. There is an ABI mismatch between the OpenMPI that comes with the system (compiled with GCC 8.5.0) and the current GCC 9.3.0, resulting in MPI_Finalize when double free crash. In addition, non-GPU-aware MPI requires CPU↔GPU data copy during each communication step, which results in huge communication overhead.

DTK 25.04.2 does not come with the UCX library. Test environment passed <UCX_MODULE> provides UCX components with ROCm transport layer. OpenMPI 5.0.7 by --with-ucx and --with-rocm links related components to achieve GPU-aware communication.

10.9 gfx906/Z100: Same-node solution without UCX ROCm

Platform B lacks static libhsakmt.a, does not build the UCX ROCm transport layer. OpenMPI still recognizes device pointers via the ROCm accelerator extension and uses shared memory within the same node:

./configure --prefix=<USER_HOME>/softwares/mpi/ompi-install \
  --enable-mpi-fortran=no \
  --with-rocm=<DTK_ROOT> \
  --with-slurm

export UCX_TLS=sm,self
mpirun --mca pml ob1 --mca btl vader,self \
  -np <GPU_COUNT> lmp -in input \
  -k on g 1 -sf kk -pk kokkos gpu/aware on

This build is confirmed to deliver accelerator: rocm and mpiext: rocm. It is intended for intra-node 1–4 card P2P testing and does not represent cross-node RDMA validation.

Recommended solution

Within the range of hardware, software versions and workloads described in this report,KOKKOS + HIP + neigh/transpose on achieved the best overall performance.

12.7 Key Lessons

⚠️ LJ is not suitable for GPU benchmark: The GPU is only 20% active, and the optimization effect is amplified
⚠️ EAM is a reasonable GPU benchmark: GPU active 41%, Pair accounts for 36.8%
⚠️ Device utilization during the active computing phase can approach 100%(HIP trace sampling), but end-to-end performance is still limited by CPU-side framework overhead (Modify accounts for 57-76%)
⚠️ Video memory precedes computing power bottleneck: 32M neighbor list initial allocation 256GB > 64GB
⚠️ Multi-GPU three conditions: GPU-aware MPI + compute-intensive potential function + large number of atoms (>500K per GPU), both are indispensable
⚠️ GPU package vs KOKKOS: The GPU package has good scalability but a single card is slow. KOKKOS is fast with a single card but poor with multiple GPUs.

12.8 gfx906/Z100 known limitations and bypasses

CHARMM/Kokkos neighbor list

12.9 Summary of dual platform experience

✅ First distinguish the architecture support status: gfx906 has been natively supported by Kokkos; gfx936 needs to register the architecture, wavefront and system allocation attributes, and the two cannot reuse the same patch assumption.
⚠️ DTK upgrades may have no performance gain or may introduce build regressions: The performance of 25.04.4/26.04 on platform A is basically unchanged, but 26.04 on platform B introduces the cuda_wrappers host-mode problem.
✅ Heavy HIP compiled and placed on computing node: The shared login node memory will fluctuate violently with concurrent users; resource applications must comply with the site CPU×memory upper limit and explicitly pass the exit code.
✅ GPU-aware does not have to rely heavily on UCX ROCm: Platform B via OpenMPI --with-rocm and shared memory implement same-node GPU-aware; Platform A verifies the UCX+ROCm path.
⚠️ Self-compiled OpenMPI to control the transport layer: Platform B uses pml ob1、btl vader,self and UCX_TLS=sm,selfto prevent unadapted InfiniBand/UCX paths from triggering GID assertions.
⚠️ Multi-card expansion depends on three conditions: GPU-aware MPI, more than about 500K atoms per card, and a sufficiently computationally intensive potential function are indispensable; video memory capacity may be the upper limit before computing power.
