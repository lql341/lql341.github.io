Hashcat HIP Adaptation and Cross-Platform Validation on Hygon DCU

covers DTK 25.04.2–26.04, gfx936 and gfx906/Z100: from ABI positioning, code adaptation and build troubleshooting, to HIP/OpenCL comparison, multi-algorithm performance and continuous load verification.

1. Executive Summary

hashcat v7.1.2 already contains HIP backend, but its built-in HIP ABI and Hygon DTK's libgalaxyhip.so , so the device initialization process cannot be completed. This work first completed the root cause location and adaptation on gfx936 + DTK 25.04.2, and then migrated the same solution to gfx906/Z100 + DTK 26.04, forming a complete evidence chain from ABI detection, conditional compilation, runtime verification to cross-version regression.

The SHA2-256 throughput difference between HIP and OpenCL in the gfx936 environment is less than 0.01%; the gfx906/Z100 environment completed 10 algorithms and 60 seconds stability verification. The two types of data answer different questions and do not make unequal back-end comparisons.

4. Code changes

follows the principle of "the default build behavior remains unchanged and DTK adaptation is explicitly enabled". The changes focus on the build entry, HIP type definition, device attribute initialization, dynamic loading and adaptation documentation.

Step 1: Add independent build switch
src/Makefile

New DTK_HIP ?= 0. Only execute make DTK_HIP=1 only when HC_HIP_DTK, normal builds still use the original ROCm ABI.

DTK_HIP ?= 0

ifeq ($(DTK_HIP),1)
CFLAGS += -DHC_HIP_DTK
endif
Step 2: Align DTK Device Property Enumeration
include/ext_hip.h

at HC_HIP_DTK The DTK attribute number actually used by hashcat is explicitly defined under the conditional branch. The original full enumeration remains at #else branch, does not affect the default ROCm build.

Step 3: Align the 792-byte device attribute structure
include/ext_hip.h

Rebuild hipDeviceProp_t, guaranteed hipGetDeviceProperties() is consistent with the hashcat reading method, especially regsPerBlock、gcnArchName and other fields.

Step 4: Compatible with missing register attributes
src/backend.c

DTK old version structure does not have regsPerMultiprocessor field, and the runtime query for attribute number 69 returns hipErrorInvalidValue. The DTK branch uses prop.regsPerBlock as conservative compatible value.

#if defined (HC_HIP_DTK)
device_param->regsPerMultiprocessor = prop.regsPerBlock;
#else
device_param->regsPerMultiprocessor = prop.regsPerMultiprocessor;
#endif
Step 5: Complete the diagnostic log
src/ext_hip.c

The diagnostic log outputs the device number and attribute number at the same time, which facilitates locating the runtime status to specific ABI items; and corrects hipGetDeviceProperties .

hipDeviceGetAttribute(dev=0, attrib=69): invalid argument
Step 6: Adjust the dynamic library to exit the life cycle
src/ext_hip.c / src/ext_hiprtc.c

DTK's HIP/HIPRTC DSO registers a C++ exit callback. hashcat advance dlclose() , libstdc++ still calls these callbacks during the process exit phase, causing a jump to the unloaded address. The DTK build therefore does not close these two DSOs early, leaving them to the operating system for recycling when the process terminates.

Step 7: Save product and adaptation documentation
.gitignore / docs/dtk-hip-adaptation.md

build product is not included in version control, and construction, verification and version boundary instructions are supplemented; the OpenCL baseline version is saved separately for regression verification and performance comparison.

5. Fault localization and debugging

  1. Confirmed binary contains HIP:Checked hipInit、hipDeviceGetAttribute、hiprtcCompileProgram , and --backend-ignore-hip parameters.
  2. Eliminate misjudgment of no-card nodes:The login node is missing /dev/kfd; After switching to the assigned computing node, the DCU and driver are normal.
  3. Create an OpenCL baseline:can identify BW through OpenCL and complete the MD5 benchmark, proving that the hardware and hashcat core functions normally.
  4. Enhanced logging post-lock enumeration:First failed attribute changes from opaque error to attrib=69, and then use the DTK header file to compile the detection program to check the value and structure offset item by item.
  5. First ABI fix:After synchronizing property enumeration with struct, device enumeration advances to register properties; runtime confirmation property 69 is not supported by DTK.
  6. register compatible processing:Auxiliary program display prop.regsPerBlock=196608, while attribute 69 returns an error, so this value is adopted as conservatively compatible data.
  7. HIP device enumeration successful:hashcat can display HIP 6.3.25422, BW, 80 MCU, 65520 MB and PCI addresses.
  8. HIPRTC Verification:MD5 and NTLM benchmark succeeded, proving that gfx936 .
  9. found exit phase SIGSEGV:The calculation result has been output, but the exit code is 139. Use GDB to locate atexit_thread.cc:75, the top of the stack is the unsigned unloaded address.
  10. Fix DSO lifecycle:DTK branch retains HIP/HIPRTC DSO until the process exits, and then the benchmark exit code returns to 0.
  11. Correctness verification:Actual MD5 dictionary attack passes self-test, and recovers e11c594e6a2f4eb499cceadfca988595:13LEXON。

6.3 DTK 26.04 Differences in environment construction and scheduling

migration platform is mutually exclusive with the newer GCC module, and the system GCC 4.8.5 lacks the AVX512F built-in functions required by the bridges module. Actual use of DTK comes with dcc(Clang 17) compiles source files, system GCC completes final archive linking; bridges are not built and do not affect the core hashing functionality covered by this report.

Compiler and Archives

dcc directly handles the final .a will be misidentified as the source file when archiving. Should remain make DTK_HIP=1 ENABLE_LTO=0 and confirming that the final linker can handle the archive.

Macro definition location

DTK attribute override macro must be placed after the enumeration definition, otherwise preprocessing will replace the enumeration member names with numbers and cause compilation failure. The bit fields or unsigned fields in the DTK struct that is not read by hashcat can be occupied by the same size type, but the total size and key offset must be checked with a probing program.

Compute node file visibility

The temporary directory of the login node is not necessarily visible to the compute node. Binary,OpenCL/、modules/ and hashcat.hcstat2 is deployed to the shared project directory; this article writes the specific user directory, partition name and node name as placeholders.

Batch and interactive jobs

Batch jobs in this environment were failing with a site-specific signal, while interactive jobs with the same resource request were running normally. The phenomenon is closer to a scheduling policy or script path problem and cannot be attributed to hashcat; when reproducing, please use the partition and resource parameters specified in the site documentation.

9. Performance verification and comparison

9.1 gfx936 same card backend test method

In order to avoid short benchmark hiding the difference between thermal stability and continuous scheduling, the 8-bit full character set brute force attack of SHA2-256 is used, and the key space is 95^8 = 6,634,204,312,890,625. Using hard-to-hit target hashes to keep the DCU fully loaded, each backend runs for about 45 seconds and passes hy-smi samples power consumption, temperature and utilization every 2 seconds.

# HIP
./hashcat-hip-dtk -m 1400 -a 3 \
  ffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff \
  '?a?a?a?a?a?a?a?a' -O -w 3 --runtime 45 \
  --status --status-timer 5 --potfile-disable --restore-disable \
  --backend-ignore-cuda --backend-ignore-opencl

# OpenCL：攻击参数相同，只切换后端和二进制
./hashcat-opencl-original -m 1400 -a 3 \
  ffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff \
  '?a?a?a?a?a?a?a?a' -O -w 3 --runtime 45 \
  --status --status-timer 5 --potfile-disable --restore-disable \
  --backend-ignore-cuda --backend-ignore-hip

10. Conclusions, recommendations and known limitations

Availability

HIP device enumeration, HIPRTC, kernel loading, actual cracking and normal exit have all passed, and the minimum adaptation goal has been completed.

Performance

In this SHA2-256 test, HIP and OpenCL are both about 5.914 GH/s, and the difference is less than 0.01%; the current data does not reflect significant performance differences.

Cross-version

DTK 25.04.2 and 26.04 are exactly the same, and the same adaptation has been reused on gfx936 and gfx906; you still need to re-detect after upgrading.

Known limitations

  • Adaptation verified DTK 25.04.2 / HIP 6.3.25422 and DTK 26.04 / HIP 6.3.26113; Future versions must still recheck the enumeration value, structure size and field offset.
  • gfx936 covers actual attacks and HIP/OpenCL comparison; gfx906 covers 10 algorithms, but lacks OpenCL comparison with the same card.
  • regsPerMultiprocessor uses conservative compatibility values; the current algorithm works fine but may affect the tuning upper limit of some cores.
  • DTK build intentionally not advanced dlclose HIP/HIPRTC DSO. This does not cause leaks outside of the process lifetime, but differs from standard hashcat's offload behavior.
  • 45–60 second test is suitable for relatively stable throughput and is not equivalent to long-term reliability testing of hours or days.
  • The old GCC migration environment does not build the bridges module, and batch jobs are also affected by the site scheduling policy; neither should be extrapolated to hashcat core limitations.

Follow-up suggestions

  1. Extended testing based on common workloads:-m 1000、-m 10900、-m 22000、-m 3200。
  2. performs 1–4 hours of stability testing on HIP and OpenCL, monitoring temperature, power consumption, driver logs, and error counts.
  3. adds automated detection or compile-time assertions to DTK ABI to prevent silent use of incorrect layout after DTK upgrade.
  4. If the goal is to gain performance improvements, further analysis of HIPRTC compilation parameters, register occupancy, wavefront behavior and dedicated tuning should be done instead of just switching backends.
