MinerU 海光 DCU 版兼容性测试报告

本报告记录 MinerU 在 CentOS 7 / glibc 2.17 超算环境中的编译安装、依赖适配与功能验证。 核心难点：onnxruntime ≥ 1.17.0 仅发布 manylinux_2_28 (glibc 2.28+) wheel，与集群 glibc 2.17 不兼容。 经过 5 条路径的试错，最终通过 Python 3.10 + onnxruntime 1.16.3 + magika 0.5.0 + 源码修改 成功安装并验证。

📜 详细编译与安装过程

成功路径、失败原因与适配修改

4.1 路径 A（成功）— Python 3.10 + onnxruntime 1.16.3 + magika 0.5.0

Step 1 · 从源码编译 Python 3.10.14
使用 GCC 11.2.0（用户安装于 <USER_HOME>/software/gcc-11.2.0-install），configure 耗时约 8 分钟（NFS 文件系统慢），make -j64 耗时约 3 分钟。注意：_ssl 模块因 OpenSSL 版本冲突（系统 1.0.2k vs /usr/local 3.0.2）编译失败，但不影响 venv 和 pip 功能。
Step 2 · 创建 Python 3.10 venv
<USER_HOME>/python-3.10/bin/python3.10 -m venv <USER_HOME>/mineru-venv-py310
Step 3 · 使用 HTTP 镜像安装 onnxruntime 1.16.3
由于 _ssl 缺失，pip 无法使用 HTTPS。改用阿里云 HTTP 镜像：pip install onnxruntime==1.16.3 -i http://mirrors.aliyun.com/pypi/simple/ --trusted-host mirrors.aliyun.com。onnxruntime 1.16.3 是最后一个发布 manylinux_2_17_x86_64 (glibc 2.17) 的版本。
Step 4 · 安装 magika 0.5.0
magika 0.5.0 依赖 onnxruntime ≥ 1.15.1, < 2.0.0，与 1.16.3 兼容。纯 Python wheel，无需编译。
Step 5 · 修改 MinerU 源码
两处修改：(1) pyproject.toml：magika≥0.6.2 → magika≥0.5.0；(2) mineru/utils/guess_suffix_or_lang.py：.prediction.output.label → .output.ct_label（magika 0.5.x 的 API 变化）。
Step 6 · 安装 MinerU + 依赖
分批安装依赖（pandas、opencv-python、pillow、huggingface-hub、modelscope 等），最后 pip install -e . --no-deps 安装 MinerU 本体。关键冲突：onnxruntime 需 numpy<2，opencv-python 需 numpy≥2，最终使用 numpy 1.26.4。
✅ 结果：MinerU 3.4.4 安装成功，magika 文件类型检测功能正常。8 个 CLI 命令可用（mineru、mineru-api、mineru-gradio 等）。

4.2 路径 B（失败）— Conda 安装 onnxruntime

尝试 conda install onnxruntime -c conda-forge
conda search/install 在 "Collecting package metadata (repodata.json)" 阶段持续超时。尝试了 defaults、conda-forge、清华镜像、阿里云镜像等 channels，均无法在 120 秒内完成元数据下载。
尝试 conda create -n mineru-py310 python=3.10
同样在 "Solving environment" 阶段超时。conda 的依赖求解器 (libmamba) 在 NFS 文件系统上运行极慢。
❌
结论：Conda 路径在某国产超算集群上不可行。网络延迟 + NFS 文件系统导致 conda 的元数据下载和依赖求解均超时。建议在同类集群上优先使用 pip + 国内镜像。

4.3 路径 C（失败）— Singularity 容器化

singularity pull docker://ubuntu:22.04
Apptainer 1.1.7 可用，但 registry-1.docker.io (Docker Hub) 被墙，TCP 连接超时。FATAL: pinging container registry registry-1.docker.io: dial tcp 内部地址已省略:443: connect: connection timed out。
尝试 jsdelivr CDN 下载 python-build-standalone
GitHub Releases 下载速度极慢（< 10 KB/s），jsdelivr CDN 返回 404。无法快速获取预编译的 Python 3.10。
❌
结论：容器化路径受限于 Docker Hub 不可达。替代方案（本地构建镜像 → scp 到集群 → singularity build）可行但时间成本高，当前未深入。

4.4 路径 D（失败）— Python 3.8 + onnxruntime 1.16.3

Python 3.8.10 可用（module load python/3.8.10）
集群自带 Python 3.8.10 模块，无需编译。onnxruntime 1.16.3 有 cp38 manylinux_2_17_x86_64 wheel。
setuptools 版本不兼容
MinerU 的 pyproject.toml 要求 setuptools ≥ 77.0.3。但 setuptools 从 75.3.4 起已停止支持 Python 3.8（EOL）。Python 3.8 最高只能安装 setuptools 75.3.4。
requires-python ≥ 3.10
MinerU 的 pyproject.toml 声明 requires-python = ">=3.10,<3.14"，Python 3.8 不满足最低版本要求。
❌
结论：Python 3.8 版本过旧，无法满足 MinerU 的构建系统要求。此路径不可行。

4.5 路径 E（失败）— Python 3.12 + onnxruntime 1.17.0 强制安装

pip install onnxruntime==1.17.0
pip 的 compatible tags 机制过滤掉了 manylinux_2_28 wheel（因为当前系统 glibc 2.17 不兼容），返回 "No matching distribution found"。
pip download --platform manylinux_2_28_x86_64
可以手动下载 wheel 文件 (6.8 MB)，但下载速度极慢（~30 KB/s，从 files.pythonhosted.org）。下载到 748 KB 后放弃。
❌
结论：即使下载成功，onnxruntime 1.17.0 的 .so 文件在 glibc 2.17 上也无法加载（缺少 GLIBC_2.28 符号）。理论上可用 patchelf 修改 ELF + 提供新版 glibc 的 LD_PRELOAD，但复杂度高，未深入。

已知限制与注意事项

当前方案的边界和风险
限制项影响缓解措施
_ssl 模块缺失 pip 无法使用 HTTPS 镜像；Python 无法建立 SSL 连接 使用 HTTP 镜像（阿里云 http://mirrors.aliyun.com/pypi/simple/）；或重新编译 Python 指定 --with-openssl=/usr/local
magika 0.5.0 模型较旧 PDF 短字节序列可能被误判为 txt；其他文件类型识别准确率可能略低于 0.6.x MinerU 内置 PDF_SIG_BYTES 兜底检测；对于完整 PDF 文件影响较小
numpy 版本冲突 onnxruntime 1.16.x 需要 numpy<2，opencv-python 5.x 需要 numpy≥2 当前使用 numpy 1.26.4，opencv-python 可正常运行（警告可忽略）
[core] 依赖未安装 torch、transformers、accelerate 等 VLM 依赖缺失，CLI 和 VLM 功能不可用 需额外安装：pip install torch transformers accelerate；注意 DCU 需 DTK 版本的 torch
pip 全局配置冲突 集群 pip.conf 指向豆瓣源（已挂），每次 pip 命令需显式指定 -i 镜像 设置环境变量 PIP_INDEX_URL 和 PIP_TRUSTED_HOST；或修改 ~/.pip/pip.conf
NFS 文件系统慢 configure、conda、源码编译等操作在 /public 上极慢 考虑在 /tmp 或计算节点本地磁盘上执行编译任务

经验总结与建议

在同类国产超算集群上部署 Python 软件的通用经验

通用经验

1. glibc 版本适配是首要检查项
CentOS 7 集群的 glibc 2.17 是常见瓶颈。在安装任何有 C 扩展的 Python 包前，先检查其 wheel 的 manylinux 标签。 优先选择 manylinux2014 (glibc 2.17) 或 manylinux_2_17 标签。
2. pip 优于 conda
conda 在 NFS 文件系统上依赖求解极慢，且国内镜像不稳定。 pip + 阿里云/清华 HTTP 镜像的组合更可靠。
3. 准备多个 PyPI 镜像
阿里云 HTTP 镜像速度快且支持 HTTP；清华镜像版本较旧但稳定； PyPI 官方源速度慢但版本最全。建议按优先级配置多个镜像。
4. 预编译 Python 版本
在集群上编译 Python 耗时且不可靠（NFS 慢、依赖缺失）。 建议使用 python-build-standalone 的预编译版本，或维护一个内部 Python 安装包。
5. 容器化是长期方案
Docker Hub 被墙，但可以本地构建镜像后 scp 到集群，用 singularity build 转换。 或使用内部 Harbor registry 推送镜像。
6. 善用 --no-deps 分批安装
对于依赖复杂的大型项目（如 MinerU），先分批安装依赖，最后用 --no-deps 安装目标包， 可避免依赖解析超时和源码编译卡死。

对 MinerU 的建议

向上游提交兼容性建议：magika 的核心功能（文件类型检测）对 onnxruntime 版本的依赖并非硬性需求。 magika 0.5.0 与 0.6.x 的 API 差异仅在于返回对象结构（.output.ct_label vs .prediction.output.label）， 核心模型接口一致。建议 MinerU 考虑放宽 magika 版本约束，或提供兼容层。
