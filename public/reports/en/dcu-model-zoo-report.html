Technical report · domestic accelerator porting · 2026-11-15

LLM Inference Engines on Hygon DCU gfx936 — Cross-Engine Benchmarks and Failure Analysis

Porting 20 open-source models onto a single domestic accelerator generation (GCN gfx936, 64 GiB HBM): cross-engine benchmarks, root-cause analyses of two long-misattributed failures, the measured performance envelope, and 59 reproducible engineering constraints.

01 Abstract

This report documents porting 20 open-source models onto a single domestic accelerator generation, covering three workload classes: text generation and understanding, image and video generation, and speech recognition and alignment. The evaluation criterion is maximum inference throughput subject to an acceptable accuracy tolerance.

The work yields two reproducible throughput improvements: a 10.5% gain at the 16K/c8 tier for Kimi-Linear-48B on SGLang, and a 13% reduction in wall-clock time for a 60-item speech transcription subset with no visible CER/WER degradation. It also identifies two failures that had long been misattributed: the periodic crash at high-concurrency long context stems from per-process cumulative state rather than scheduling parameters or batch size, and the 61% single-stream deficit of the same model on vLLM stems from a fixed overhead of roughly 24 ms per decode step, unrelated to attention kernel efficiency.

Two entries on the SGLang path trigger a GPU memory fault during startup. Eight controlled experiments ruled out node, parameters, memory capacity, graph capture, and target architecture before the investigation was closed. The reason for stopping is that delivery does not depend on that path, while the reload cost per diagnostic run and the uncertainty in node disk headroom had turned the marginal benefit negative.

Keywords: heterogeneous accelerator porting; inference engine comparison; long-context failure; parameter tuning; reproducibility

02 Background and Objectives

The maturity of a domestic accelerator ecosystem is currently judged by two measures: whether mainstream open-source models run directly, and how runtime throughput compares with an established GPU platform. The first determines usability; the second determines economics. This work establishes a reusable porting path for the first and quantifies, then attributes, the gap in the second.

No model training or fine-tuning is involved; only inference-side adaptation and tuning. The accuracy constraint is that no throughput optimization may introduce a measurable degradation in output quality.

Criterion for "accuracy unchanged"

For entries with an official evaluation checklist, the criterion is official artifact specification checks plus self-computed CER/WER. For entries without an official baseline, the accuracy threshold is not determinable; the relevant sections remain unevaluated and state the reason rather than filling in estimates.

02.1 Three core questions

The report is organized around three questions:

  1. Does it run.Which models load directly with their original framework, and which require adaptation, patches, or a purpose-built runtime.
  2. How large is the gap.How much do throughput figures differ between inference engines for the same model, and is the direction consistent.
  3. Why the gap.Whether it comes from missing hardware features, software configuration, or inherent engine design.

03.2 Benchmark protocol

Text entries use a six-tier benchmark: input length {4K, 16K} × output length 1K × concurrency {1, 8, 64}, two consecutive rounds per tier, second round recorded. The client is sglang.benchmark.serving throughout, with random-token load requiring no external dataset. vLLM entries reuse the same client through a two-container arrangement so that figures from both engines are comparable.

Each tier must pass a validity check before being recorded: mean TTFT non-zero, and throughput within the physical ceiling. That check never actually ran in earlier versions because of script defects; it was repaired this round and verified against two hand-constructed anomalous samples.

03.3 Variant decision rules

Every variant comparison uses the same node, same image, and same time window, with the in-job control as the denominator and never a historical archive value. The decision threshold is a 2% relative difference; where the historical spread of that tier already exceeds the threshold, a single measurement does not settle the question.

Practical effect of the rule

The 16K/c64 improvement in section 04.1 is 2.7%, below that tier's historical spread of ±5%, so the baseline value was not changed; only the magnitude is recorded. This is the one case this round where an improvement was measured but not adopted.

03.4 Experiment orchestration

Every experiment is fixed as a self-contained job script. Each variant comparison includes:

  • Node headroom self-check — exit with a non-zero status below the threshold so the scheduler re-queues on another node.
  • Image preload and verification — both the server and benchmark-client images must be ready; failure of either aborts.
  • Server log capture — for later verification of the effective compilation mode, batch size, and KV capacity.
  • Variant isolation — each variant starts a fresh server process, preventing state from carrying across variants.

The repository copy must be synchronized to the compute side before submission, otherwise the job loads a stale script. That step was once missed, and the validity check ran a whole afternoon with an undefined variable.

04.1 Parameter tuning: chunked prefill

--chunked-prefill-size 4096 executes prefill in 4K slices and interleaves them with decode, smoothing KV cache pressure at long context. An earlier five-variant comparison had already shown a gain, but the setting was never written into the delivered configuration. This round repeated the A/B on the same node.

Secondary metrics move the same way: mean TTFT at 16K/c64 falls from 101.7 s to 91.2 s (−10.3%), p99 TTFT from 188.6 s to 172.3 s.

Baseline value left unchanged

The A variant of this round measured 222.45 at 16K/c64, which is 5.0% below the archived value of 234.17, while that tier's historical spread is ±5%. Against that background a 2.7% relative improvement cannot be separated from node-to-node variation. Writing 228.40 into the baseline would freeze a single node's deviation as long-term data. The baseline stays at 234.17 and only the parameter's effect is recorded in the entry documentation.

Correction to the accuracy claim

An earlier record stated "zero accuracy change", which is too strong. The claim now reads "metrics unchanged; 1 of 60 items differs at punctuation level".

05 Root-Cause Analysis

05.1 Periodic failure at high-concurrency long context

On Kimi-Linear-48B at 16K/c64 the observed behaviour is that the first run completes normally and subsequent runs reliably trigger a GPU memory fault (KERNEL VMFault). All four tensor-parallel ranks fault simultaneously at different addresses.

The initial hypothesis was an oversized single batch. Five configurations were tested accordingly: default, graph capture disabled, and batch limits of 24, 16, and 32 with graph capture disabled. The five configurations crashed at 29, 62, 23, 16, and 31 requests respectively.

Hypothesis refuted

The five crash points bear no relation to the concurrency limit of each configuration. In the case where the limit was 16, the crash point was exactly 16 running requests, indicating the crash occurs at the limit rather than near it. The batch-size hypothesis does not hold.

Re-examining the complete server log (about 3 MB) of an earlier continuous benchmark job produced the decisive fact: that job ran six tiers in sequence on a single server process, started at 10:30 and crashed at 11:02:58 after completing 10 tiers and roughly 1200 requests; the crash occurred in the first round of 16K/c64. Because later jobs ran only a single tier (128 requests, about 10 minutes), "first round always passes, second always crashes" was an artefact of narrowed observation.

The revised hypothesis: the failure correlates with the process's cumulative processed volume, not with round number or batch size.

Table 6　Four rounds, each on a freshly started server process (output tok/s)
RoundThroughputTTFTTPOTNote
R1235.1447.5 s218.3 mspage cache cold; not a steady-state reference
R2283.5331.5 s187.4 ms

All four rounds completed 128/128 requests with zero memory faults. R2 through R4 span a relative range of 1.2%, a repeatable steady-state band of 283.53–286.84 tok/s.

Conclusion: the failure originates in per-process cumulative state. The delivery protocol is "single round plus a server restart between rounds".

05.2 Quantitative attribution of the single-stream gap

Kimi on vLLM measures 40.73 tok/s at 4K/c1 against 104.67 on SGLang, a 61.1% deficit. The initial conjecture was poor attention-kernel efficiency at low concurrency. Breaking TPOT down by configuration refutes it.

Table 7　TPOT as a function of batch size and context length
ConfigurationvLLM TPOTSGLang TPOTObservation
4K / c124.18 ms9.31 msthe initial gap
4K / c824.96 ms20.97 msvLLM barely moves
16K / c125.23 ms—insensitive to context length

A linear fit gives 24.07 ms + 0.111 ms/request for vLLM and 7.64 ms + 1.67 ms/request for SGLang. vLLM therefore pays roughly 24 ms of fixed cost per decode step with a very low marginal cost per request, while SGLang pays only 7.6 ms fixed but an order of magnitude more per request. That structure explains the two opposing observations: vLLM wins as batches grow, SGLang wins at single stream.

Dividing 24 ms by 27 layers gives about 0.89 ms per layer, consistent with per-layer eager kernel launches plus tensor-parallel collective synchronization. The mechanistic clue is in the server startup log: 

CUDAGraphMode.FULL_AND_PIECEWISE is not supported with
  TritonMLABackend backend (support: AttentionCGSupport.NEVER);
  setting cudagraph_mode=PIECEWISE

The entry contains seven MLA layers whose decode attention cannot enter a complete captured graph and can only be captured piecewise, leaving the remainder to be launched eagerly at every step.

This yields a single-stream ceiling of about 1000 / 24.2 ≈ 41 tok/s. The measured 40.73 sits against that ceiling, further indicating the bottleneck is this fixed cost and not any component reachable by parameter tuning.

Distinction from an existing conclusion

A separate record covers long-context performance of another model on vLLM, where TPOT rises from 47.9 ms at 4K to 119.3 ms at 16K, clearly context-dependent, with a missing paged-attention kernel as the root cause. The TPOT discussed here is constant at 24 ms and independent of context. The two root causes differ and neither implies the other.

05.3 Measured effect of scheduling async

One mitigation was tested against that fixed overhead: asynchronous scheduling (--async-scheduling). The other candidate, enabling a compile mode, was excluded before measurement: the entry's compilation mode is already VLLM_COMPILE, so there is nothing further to enable.

The two observations point in opposite directions, which corroborates the attribution in 05.2:

  • The concurrent tier gains substantially. c8 throughput rises 23.2% while TTFT falls 61.7%, showing that overlapping the scheduling layer with compute removes a large amount of waiting.
  • The single-stream tier barely moves. c1 TPOT falls only 3.2% (24.35 → 23.58 ms). If the 24 ms comes from per-layer eager launches and tensor-parallel synchronization, async scheduling cannot reach it, and the measured 41.63 tok/s sits against the ceiling derived in 05.2.
Scope of the conclusion

Scheduling async is a reasonable default for concurrent workloads on this entry, but it does not resolve single-stream latency. Single-stream performance remains bound by the engine-level limitation that attention layers cannot enter a complete captured graph, which requires a purpose-built image or a different kernel path.

05.4 Startup memory fault (unresolved)

The SGLang path for Recon2Reason-4B and RoboBrain2.5-8B returns 503 on the health check from startup and the process aborts after about 20 seconds. The crash call chain is: 

radix_attention.py:127       forward
 → triton_backend.py:1199   forward_decode
  → decode_attention.py:771 decode_attention_fwd
   → decode_attention.py:712 decode_attention_fwd_grouped
    → decode_attention.py:612 _decode_softmax_reducev_fwd    ← JIT compile point
     → triton/runtime/jit.py:861 _do_compile
      → HSA_STATUS_ERROR_EXCEPTION → KERNEL VMFault

kernel: _fwd_grouped_kernel_stage1
grid:   x:16384, y:8, z:16

Eight controlled experiments were run to locate the cause:

Table 9　Exclusion experiments
HypothesisControl result
Node faultIdentical behaviour on three different nodes
Graph captureCrashes identically with graph capture disabled
Launch parametersMatch the successful run item by item: KV capacity 331k tokens, 9.44 GB free, same capture batch list

Taking the exclusions together, the most likely chain is that the runtime JIT cache path moved from "compile fails, fall back" to "compile succeeds, execute" after a configuration change. The historical successful log contains a record of the toolchain not being detected, indicating the simple indexed-assignment path was used; the current compiler path is detectable, JIT emits target code, and that code performs an out-of-bounds access on gfx936.

Limitation of this judgement

The chain above is inferred from indirect evidence and has not been verified directly. A second unresolved clue is the crashing kernel's grid x=16384: the y and z dimensions map to head tiling and KV splits, but x is the decode token count, which under this configuration should not exceed 256; 16384 matches only the prefill token limit. If that reading is correct, the crash occurs on a prefill-sized batch, pointing at an engine shape-handling difference between versions rather than at compiler code generation.

05.5 Image reproducibility check

During the experiments an archived image digest appeared not to match the locked record and was briefly recorded as a risk of upstream replacement. A complete check shows the judgement was wrong.

Table 10　Two digest conventions
ConventionMeaningShould they be equal
Registry manifest digestDigest of the manifest in the registry, used for exact pullsthis is what the lock records
Local container-config digestImage config digest recomputed locally after loadingnever equal by design

The verification compares the hash of the config file inside the archive against the config digest referenced by the registry manifest; they match. Streaming the first layer out of the archive and comparing it byte for byte against the archived first layer also matches. The archived and registry images are therefore the same object, and the digest difference is a measurement-convention issue.

Check results
  • Archive integrity check passes 11/11; all five image archives are intact.
  • All five config digests match the registry manifests, demonstrating they were not rebuilt.
  • No entry pins its pull by digest, a systemic risk: an upstream retag silently swaps the image.
  • Some entries point their archive path at a reclaimed account location and are effectively single-source.

06 Stopping Criteria and Limits

06.1 Why the two entries were stopped

Investigation of the problem in 05.4 was terminated on three grounds:

  1. Delivery does not depend on that path. The vLLM counterpart of both entries has completed the full six-tier benchmark, and the SGLang side's historical data and artifacts are preserved intact.
  2. Diagnostic cost exceeds expected benefit. Each diagnostic run must reload the 8.5 GB image archive, while node root-partition headroom varies between 0 and 278 GB; three runs were interrupted for lack of space. The parameter gain being investigated was expected to be single-digit percent, and the model is limited by single-card KV capacity (331k tokens against 1.11M needed for 64×17K).
  3. Alternatives cost more. A real fix requires first resolving image reproducibility and compiler-toolchain version matching, which is a separate project.

If reopened, attempt the following two in descending order of expected success:

  • Force the GPU backend to CUDA through an environment variable (and leave the CUDA home unset) to reproduce the historical "JIT fails and falls back" state. Estimated success 60–70%.
  • Clear the Triton compile cache, point the cache directory at local disk, and force recompilation to exclude stale target code. Estimated success 35–45%.

07 Methodological Issues

Several judgement errors occurred during this investigation whose causes are general, so they are recorded separately.

07.1 False regularities from narrowed observation

The regularity "first round always passes, second always crashes" held across three jobs and was therefore treated as a stable phenomenon. It was in fact an artefact of a narrowed observation window: the earlier job executed six tiers in sequence while later jobs executed a single tier, and only the former exposed the real variable, cumulative processed volume. Inferred from the later jobs alone, no number of hypotheses would have converged.

The corresponding practice: when several competing hypotheses exist, design an experiment that separates them before adding verification along the most intuitive direction.

07.2 Silent parameter failure

An audit of launch configuration across all entries found three modes of parameter failure, all sharing the property that no error is produced:

Table 12　Three modes of parameter failure
ModeInstanceConsequence
Same variable exported twiceOne extra-arguments variable defined twice in the same fileThe earlier definition is wholly overwritten
Launch command ignores the variableLaunch command inlines its arguments; the variable's reference count is zeroEditing the environment file has no effect
Log written outside the repositoryServer log lands outside the working directoryEffective values cannot be verified

One instance is representative: a configuration file noted "the attention backend must be specified explicitly, otherwise the first decode request crashes", and that line never executed because of the mechanisms above. The service ran because the image version changed afterwards, so the restriction no longer existed. A wrong constraint therefore persisted in the documentation.

07.3 Recording a defect as design

The most consequential judgement error of this round concerned a toolchain detection error. The line appeared in a successful run's log, from which it was inferred that compile failure is the normal fallback path and the service depends on that failure to run.

The inference is wrong on two counts. The compute stack is HIP/ROCm, which has no CUDA, so the message is a false negative from toolchain detection. And a system that depends on a compile failure to function is in an unexpected state, which should not be recorded as design. The correct direction is to point the toolchain at the right compiler so compilation succeeds and produces correct code.

Writing a defect into documentation as experience costs more than omitting it: later work optimizes along the wrong direction and cannot easily notice.

07.4 Infrastructure constraints

Failures caused by storage placement were consistent and can serve as fixed rules for similar jobs:

Container storage and data storage must be separated

Image storage can only live on node-local disk. On a shared network file system the overlay driver reports unsupported extended attributes and the vfs driver reports a permission denial on the mount point; both were confirmed empirically.

Experiment data must live in the shared home directory. A single image expansion occupies 20–32 GB; repeated expansion on node-local disk exhausts the root partition. One misstep during these experiments drove a login node from 84% to 99% usage. Rootless container storage directories also cannot be removed with a plain delete command; the engine's own reclaim commands must run first.

Job templates should include a node headroom self-check and exit with a non-zero status below threshold, so the scheduler re-queues elsewhere. Exiting deliberately is easier to clean up than failing mid-write.

07.5 Falsifiability of conclusions

Every variant comparison requires same-node, same-window, in-job controls plus a report of that tier's historical spread. The practical effect is that when an improvement is smaller than the spread, the conclusion must be marked as not credible. The 2.7% in 04.1 is such a case: directionally positive, but not recorded as an available improvement.

08 Conclusions and Further Work

08.1 Main conclusions

  1. Parameter gains are limited but real. Chunked prefill yields 10.5% at 16K/c8, beyond that tier's spread; speech batch concurrency tuning cuts wall time 13% with metrics unchanged. Both were settings that had been measured but never adopted.
  2. Long-context high-concurrency failure comes from process cumulative state. Restarting the server per round produces stable figures with a 1.2% spread across four rounds, refuting the earlier batch-size hypothesis.
  3. Engine superiority depends on the workload tier. For the same model the gap between engines reaches a factor of three and reverses direction. Engine choice must follow the actual load distribution rather than a single metric or an average.
  4. Two entries had one engine path stopped. Eight controlled experiments excluded the conventional hypotheses; the remaining doubt points at toolchain and image version matching, whose cost exceeds this round's scope.
  5. Image reproducibility holds after checking. The earlier digest mismatch was a measurement-convention difference, not replacement. However, no entry pins its pull by digest, a systemic risk requiring remediation.

08.2 Further work

Three directions
  • The parameter-sweep gap. The vLLM path of the two vision entries has had no parameter sweep at all; its chunked-prefill granularity is still the default. With the other engine path stopped, vLLM is the only avenue.
  • Two remaining candidates for single-stream overhead. Beyond scheduling async, which was measured in 05.3, collective-communication parameters remain untested against the 24 ms fixed cost. The compile-mode candidate is void: the entry already runs in that mode.
  • Pin image pulls by digest. Switching all entries to digest-based pulls removes the risk of an upstream retag silently swapping the image.

08.3 Data verifiability

Every figure in this report can be verified: the raw six-tier records, entry-level metadata, and the server logs of each experiment are retained alongside the code repository. The full list of engineering constraints is ordered by how hard the problem is to spot, each entry giving the symptom, the exclusion process, and the criterion.
