vLLM 0.27.x 开发版经 gfx936 / DTK 定向适配，V1 Engine 已完成真实 FP4 权重端到端推理

FP4 MoE 当前使用 emulation，FP8 主干采用 BF16 software fallback。“跑通”指真实模型、真实权重和完整生成链路通过，并非仅完成 kernel 单测或模型加载。

3关键修复与验证

3.1 Sparse MLA KV cache 物理布局

逻辑宽度为 584B，但真实存储是 data 与 scale 分区：

[block_size × 576B token data][block_size × 8B scales]

data  = block_base + position × 576
scale = block_base + block_size × 576 + position × 8

旧 reader 按 584B 交错读取会得到错误 scale，进而出现 NaN、异常 RoPE 和持续 BOS。修正地址后端到端链路恢复。

3.2 gfx936 Triton manual E4M3 decode

避免不可靠的 FP8 bitcast lowering，改用手工 OCP E4M3 解码。全 256 byte 对拍为 max_abs=0、bad_count=0；真实 cache 单层 cosine 为 0.99999750，相对 PyTorch reference 约 3.30×。

3.3 M=1 MoE routing Q1

decode 时一次读取 6 个 expert ID，绕过高频 unique / nonzero / index_select。门禁为 max_abs=0、cosine=1、bit_equal=True，已进入稳定配置。

5batch=8 正确性边界

batch=1–7 未出现 BOS 型结构失败；batch=8 在较长 decode 后可出现 BOS、模板退化或 NaN。短输出 2/4/8 token 正常，12 token 曾首次观察到 BOS，但精确长度边界重复实验又能通过，说明问题不是简单的固定 shape 边界。

  • PyTorch Sparse reader 下问题仍存在，排除 Triton Sparse batch indexing 是唯一根因。
  • MXFP4 的 M=1…9 对拍通过，排除 M=8 GEMM 的直接确定性错误。
  • NaN 在 sampler 之前已出现，范围收敛到模型前向链路。
  • 当前优先怀疑异步 stream、workspace 复用或 kernel race。

公开报告只发布已验证的单请求性能。batch 吞吐在通过 token IDs、BOS、finite、退出码和重复运行门禁前均视为探索数据。

7下一阶段
  1. 恢复可用调度资源后，扫描 TP=4/8 与可扩展 batch 的 aggregate tok/s。
  2. 对最快候选执行完整 token、BOS、finite、退出码与重复运行验收。
  3. 围绕 43 层 MoE 减少临时张量、Python 调度和 kernel launch。
  4. 继续定位 batch=8 非确定性问题，建立 P50/P95 TTFT、TPOT 与吞吐基准。
  5. TP=8 聚焦高并发及 collective；单请求维持 TP=4 基线。
